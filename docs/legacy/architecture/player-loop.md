# M2-A 玩家更新与交互循环

> 历史架构参考：M2-A。文中的“当前”指该阶段，不代表最新实现；归档不表示相关机制全部废弃。源码链接保留定位用途，不固定历史版本或行号。参见 [历史架构索引](README.md)；后续设计约定见 [项目范围](../../spec/project-scope.md)，不据此推定重构已经完成。

本文说明 M2-A 对现有玩家循环的局部修正。目标是让输入、物理、相机和方块交互使用同一帧的数据，并限制长帧恢复的工作量；不是重写一个通用物理引擎，也没有引入多线程、动态地图或新玩法。

实现与自动测试代码已提供。编译、自动测试和人工玩法的实际结果由里程碑记录统一发布，本文不将源码检查或测试用例存在等同于验收通过。

## 1. 职责与调用顺序

```text
窗口事件与焦点状态
    |
    v
输入 -> 玩家 movement_axis / yaw / pitch / jump 请求
    |
    v
TransformSystem::Update
    | 更新当前玩家方向基
    v
Character::Player::Update
    | 根据输入计算速度，消费跳跃请求
    v
Physics::Update(registry, frame_delta)
    | 有限次数的 120 Hz 物理步，更新位置与接地状态
    v
Character::Player::SyncCamera
    | 将最新玩家位置、角度和方向基复制给相机
    v
PlayerController::DoRayCast
    | 用本帧视角选块、拆放
    v
区块网格更新 -> 渲染
```

此前角色更新同时负责速度和相机位置，主循环又在 Transform 更新前做射线检查，容易出现物理、相机或编辑目标使用旧数据的情况。现在将“速度与跳跃意图”和“相机同步”明确分开。

`SyncCamera` 不只复制 `yaw`、`pitch`，还复制 `front`、`right`、`up`。因为投影前的视图计算直接使用这些向量，仅复制角度会让相机继续等待下一次 Transform 更新。

本模块假定单个本地玩家。多个 `PlayerComponent` 将依次写同一个应用相机，当前不把它解释为多玩家或分屏支持。

### 键盘快照与短按

普通 `glfwGetKey` 只反映最近的按键状态。如果一次 `glfwPollEvents` 同时处理按下和松开，随后的轮询可能只看到“松开”，导致短按 Esc、Space 或材料切换键没有进入游戏逻辑。

当前启用 GLFW 的 `GLFW_STICKY_KEYS`。它会把尚未读取的按下保留到一次 `glfwGetKey` 查询，松开后的保留状态在查询后消费。这里使用的是 GLFW 自带输入能力，不进行操作系统级按键注入。

读取也必须配套改变：[key_snapshot.h](../../../include/input/key_snapshot.h) 每帧完整采样 11 个控制键各一次，然后所有玩法条件只读取这份不可变快照。不能继续在 W/S 三元表达式、Caps Lock/Ctrl 条件或提前退出分支里直接读取 GLFW，否则短路求值可能将 S、Ctrl 等未读取的 sticky 状态留到后面某帧突然触发。

失焦处理有顺序要求：仓库自带 GLFW 在调用焦点回调后，还会合成按键释放事件。这些释放也可能建立 sticky 状态。因此焦点回调只记录“需要清输入”，真正清理在事件轮询结束后的暂停或恢复分支执行：临时关闭再打开 sticky，清除玩家请求和水平速度，重置物理余量与鼠标首次进入状态。即使失焦和恢复发生在同一次事件轮询中，也会根据标志清理，避免恢复后补触发旧跳跃、材料切换或退出。

这解决的是按键采样丢失，不改变原玩法前置条件：Space 仍需接地；Q/E 仍受 0.2 秒防抖限制；没有新增空中跳跃缓冲或排队执行多次材料切换。

连续移动与瞬时操作还存在区别。短按 W/S 只保证有一帧能读到它；若该渲染帧没有累计足够的 120 Hz 物理步，而下一帧已经松开，可能仍没有位移。本阶段不为了极短自动化点击而强行推进一个物理步，也不扩大为带时间戳的输入回放系统。移动验收应使用足够持续的按住操作；Esc、材料切换直接在帧内生效，已接受的跳跃速度会保留给后续物理步，不依赖该帧必须立即推进物理。

## 2. 接口与所有权

| 接口 | 责任 | 约束 |
| --- | --- | --- |
| `Character::Player::Update(registry)` | 计算水平速度、处理现有无碰撞下降、消费跳跃请求 | 在玩家 Transform 方向更新后、物理前调用 |
| `Physics::Update(registry, frame_delta)` | 根据经过限制的物理步数执行积分和体素静态碰撞 | 时间单位为秒；不再读取应用全局 `delta_time` |
| `Physics::ResetTiming()` | 清空不足一个物理步的累计时间 | 世界准备完成、暂停或失焦时调用，避免遗留时间进入恢复帧 |
| `Character::Player::SyncCamera(registry)` | 同步物理后的玩家位置与当前方向 | 在物理后、渲染前调用，不消费输入 |
| `Physics::RayCastStatic(origin, direction, max_distance, draw)` | 查询有限距离内第一个可交互实心体素 | 方向可以不是单位向量；`draw` 参数保留接口兼容，当前不额外绘制射线 |
| `PlayerController::DoRayCast(registry, window)` | 将命中结果变为选择框及经过约束的拆放操作 | 仍采用原来的鼠标优先级与防抖时间 |

Registry 继续拥有 Transform、RigidBody、HitBox 和角色组件。本模块只在一次调用期间借用引用，不创建后台任务或保留跨帧的组件引用。

物理计时器是 `physics_system.cpp` 内部对象，由 `ResetTiming` 管理其少量状态。它不是多个世界共享的通用时钟，也没有并发访问保证。

## 3. 有上限的固定物理步

保留原有 `1/120` 秒的物理步长，以及重力、最大速度、步行、奔跑和跳跃参数。计时策略实现于 [player_math.h](../../../include/playercontroller/player_math.h) 的 `FixedStepBudget`：

1. 拒绝负值、零值或非有限帧时长，不推进模拟。
2. 每次至多接收 8 个物理步对应的时间，即约 66.7 毫秒。
3. 累计不足一个步长的余量，供下一帧使用。
4. 每帧至多执行 8 步，不保留超量长帧造成的无限积压。

这个设计优先保证恢复能力。窗口阻塞数秒后，游戏不会试图在一个渲染帧中补算数百步。代价是长期低于约 15 FPS 时，模拟可能慢于真实时间；不能把此策略描述成完整追赶或确定性输入回放。

应用层仍需负责在世界和首批网格准备完成后开始计算帧时间，并在失焦、最小化时清输入、暂停和重置计时。物理内部的步数限制是第二层保护，不替代应用层暂停策略。

不应把经过截断的模拟时间当成真实性能帧耗时。后续性能采集应另存真实墙钟耗时，明确哪些时间被用于模拟。

## 4. 移动、跳跃与接地

### 移动

`DesiredVelocity` 根据玩家 yaw 构造地面前方与右方向，再合成输入。存在水平移动时对合成向量归一化，避免同时按前进和横移比直走更快。无输入时水平速度清零。

保留现有无碰撞模式的语义：不新增向上飞行。只有垂直下降输入时维持原来每秒 1 个世界单位的速度；若同时水平移动，三维合成方向按当前步行或奔跑速度归一化。这个历史行为被测试固定下来，后续若要统一飞行手感，应作为明确的玩法改动单独讨论。

### 跳跃

跳跃请求只在“启用重力、已经接地、不是无碰撞传感器”的情况下生效。成功后立即清除 `on_ground`，设置向上速度并清除旧的下落加速度；无论请求是否成功，都会消费请求，避免在未来某帧意外触发。

保留跳跃到达顶点后增强下落的原参数。接地后清除跳跃状态和垂直加速度。这里的 `is_jumping` 延续原有含义，主要表示主动跳跃的上升阶段，不是“当前人在空中”的通用标记。

### 接地与碰撞

原有静态 AABB 碰撞解算框架继续保留。本次局部修正包括：

- 每个物理步重新建立 `on_ground`，不把过去接地状态永久保留下来。
- 加入脚底支撑检查。脚底在方块顶面约 0.002 单位容差内、且水平投影仍有支撑时，保持站立；走出支撑范围后不再接地。
- 碰撞盒中心计算计入 `HitBox::offset`，与放置保护采用相同几何约定。
- 避免对零速度向量做归一化。原来用于判断是否正离开接触面的点积，现在直接使用两个向量的点积符号。
- 无碰撞模式不保留接地状态。

接触面本身不视为体积穿透。AABB 重叠判断要求三个轴都存在正长度交叠，不能因为两个面刚好相接就禁止方块放置。

这不是连续碰撞检测，也没有实现复杂的阶梯攀爬、斜坡、多刚体或可靠的任意深度脱嵌。墙角、低顶、落到单块顶部、从无碰撞模式恢复等场景仍需人工验收，不能由脚底支撑的纯逻辑测试替代。

## 5. 体素射线与编辑目标

旧射线通过多次近似除法寻找方块，零方向分量和整数边界较难保持一致。本次使用单位网格 DDA：

1. 将射线方向归一化，使距离参数始终表示世界单位。
2. 用 `floor` 获得起始格，负坐标不使用向零截断。
3. 分别记录下一次穿过 X、Y、Z 网格面的距离，以及同方向两个网格面之间的距离。
4. 每次推进距离最小的轴；同时越过多个网格面时一起推进，避免把只碰到边或角、没有进入内部的格子误认为遮挡。
5. 查询进入的格子；第一个实心格作为命中，超过最大距离后停止。

实现接受恰好位于距离终点的命中。零向量、非有限输入和负距离直接返回未命中。对异常巨大的坐标或距离还有防止整数转换溢出的界限，实际固定地图与 3 单位交互距离远小于此界限。

零方向分量用无穷大的跨面时间表示，不参与推进。若起点恰在整数边界且朝负方向，则从边界负侧的格子开始，避免把身后的格子误判为前方目标。同一距离出现多个跨面时，法线按 X、Y、Z 优先顺序选取一个确定的面。

若射线起点在实心格内部，返回该格且距离为 0；没有确定入射面的情况下法线为零。允许拆除这个命中格，但不允许据此向某个任意方向放置。

`IsSolidVoxel` 拒绝地图高度范围外的格子，并将缺少区块、空块和空气视为不可命中。其他格子继续按现有 `BlockFormat::m_is_solid` 判定，因此没有新增水体或透明材料的交互规则。

命中结果包含明确的格子中心。拆除直接使用这个中心；放置使用“命中格中心 + 面法线”，不再通过在浮点命中点上加减 0.1 来推断目标格。

## 6. 放置保护与现有交互语义

放置前检查：

- 当前选中索引在 8 种既有材料范围内。
- 命中法线有效，目标高度在地图范围内。
- 目标不是缺失区块，并且不是已经占用的实心方块。
- 如果即将放置的方块是实心方块，其单位 AABB 不得与玩家的 AABB 有体积重叠。

这种检查避免将玩家直接封进刚放置的实心块中，也不会为了放置操作隐式创建新地图区块。非实心目标是否可以被替换仍由现有方块属性决定。

仍保留右键优先于左键、同一个防抖计时器、约 0.2 秒编辑间隔和 Q/E 选择逻辑。无效放置也会消耗本次防抖间隔，避免持续按键反复进行无意义的尝试。

## 7. 无窗口测试与边界

[player_math_tests.cpp](../../../tests/player_math_tests.cpp) 只依赖 `player_math.h` 和 GLM，不创建窗口，也不需要初始化 Registry、世界或 GPU。

| 测试组 | 已编写的覆盖 |
| --- | --- |
| 固定步预算 | 半步累计、长帧最多 8 步、下一帧无长积压、无效时间、重置余量 |
| 射线 | 六个轴方向、非单位方向、距离终点、超距拒绝、负向整数边界、斜线边角、无效输入和空世界终止 |
| AABB | 实际重叠、仅接触不重叠、负坐标分离 |
| 移动 | 直走和斜走等速、朝向旋转、奔跑参数、松键零速度、保持原垂直下降速度 |
| 接地 | 方块顶面站立、走出台阶、空中不接地 |

另外，[key_snapshot_tests.cpp](../../../tests/key_snapshot_tests.cpp) 使用消费型测试读取器检查：所有控制键只采样一次，后续短路条件不会留下旧键，重复读取快照不会再次消费底层输入，以及长按可在下一帧继续读到。它不加载 GLFW，也不替代真实焦点切换或操作系统输入的集成验证。

射线和支撑检查通过函数参数接收“某个格子是否实心”的查询。实际游戏传入区块查询，测试传入简短的固定场景函数。算法逻辑相同，数据来源不同，因此无需为测试启动完整游戏。

这个测试入口不覆盖整个物理求解器、真实输入回调、ECS 存储、相机最终画面或操作手感。它提供局部回归保护，必须与 [玩法冒烟清单](../../testing/gameplay-smoke.md) 的移动、跳跃、碰撞、交界和恢复用例共同使用。

构建接入需要将该测试源注册为独立目标，提供项目 `include` 目录、`glm::glm` 和 C++20，并加入 CTest。实际注册名称和通过记录以当前 [tests/CMakeLists.txt](../../../tests/CMakeLists.txt) 与里程碑证据为准。

## 8. 后续边界

本次没有增加固定输入回放、插值相机、物理可视化编辑器或新的碰撞库，也没有对全部历史求解代码做重新设计。后续应优先根据真实失败证据改进墙角和脱嵌，再决定是否需要更系统的物理与输入抽象。

若未来引入多个世界实例或并行任务，必须重新明确计时器所有者、区块查询的线程约束和组件引用有效期；当前实现不能直接推定为线程安全。
