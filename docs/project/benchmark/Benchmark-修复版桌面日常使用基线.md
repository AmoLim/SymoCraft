# Benchmark 修复版桌面日常使用基线

本次使用无边框窗口修复包，在开发台式机完成快速检查 3/3 和正式基线 9/9，无重试、取消或失败。正式样本约 84.47% 的时间处于失焦状态，因此定位为允许切换窗口的日常使用对照组，不作为纯前台、空闲环境下的性能基线。

## 要回答的问题

- 修复包能否在本机允许失焦但不最小化的条件下，完整执行默认 36 分钟协议，并生成可核验的新版对照数据？
- 关联功能：[[Benchmark-1080p窗口修复]]、[[Benchmark-执行与导出]]、[[Performance-失焦采样]]。
- 本次只执行已有包，不修改游戏、执行器或协议，不覆盖历史结果，也不代替朋友 1080p 原机复测。

## 假设与判据

- 支持判据：三种场景各三轮，均完成 60 秒预热和 180 秒采样；实际 framebuffer 为 1920×1080；进程正常退出，执行器校验通过；版本身份一致且未发生重试。
- 否定判据：最小化或尺寸变化导致无效、提前退出、数据缺失或统计不一致，任何一轮需要重试。
- 证据边界：允许后台应用参与系统调度，但未记录其完整负载，不能据此推导无干扰性能、切换窗口的因果影响或跨设备性能达标。

## 实验步骤

1. 将修复包解压至新的 `out/benchmarks/desktop-windowfix-20261004-0844Z/package`，核对游戏、执行器及 ZIP 哈希，保留运行条件声明。
2. 使用独立原生执行器完成快速检查，3/3 有效后开始正式采样。没有修改朋友侧入口或增加脚本依赖。
3. 顺序执行九轮；期间不构建项目、不改变游戏配置，允许用户按约定切换窗口。只轻量读取执行器进度。
4. 所有轮次结束后确认游戏和执行器退出；使用同一执行器导出结果 ZIP，并检查 ZIP 哈希及其中 82 个清单文件的内容哈希。
5. 用仓库已有 yaml-cpp 解析摘要、汇总各轮统计；读取 memory.csv 的已采集记录计算峰值。不重新筛选逐帧数据或修改原始结果。

| --- | ---: | ---: | ---: | ---: | ---: |

CPU 侧 upload / submit 计时明显大于所测 GPU draw 区间，可作为后续剖析入口，但不能仅凭此表宣布具体 CPU 瓶颈：GPU draw 不含显式上传、clear、swap，且窗口遮挡和驱动调度也可能影响实际工作量。上述数值不是 CPU/GPU 利用率。

- 从 main 入口到首次 SwapBuffers 返回，三轮中位数：static 982.64 ms、walk 967.18 ms、edit 989.43 ms；不是从用户双击到画面实际显示的延迟。

## 结论

- 判定：支持。该修复包在本机完成连续九轮有效采样，建立了版本明确、允许失焦的日常使用对照组。
- 失焦并未使本次采样被判无效；不意味着切换应用对帧时、GPU 工作量或视觉呈现完全没有影响。焦点暴露比例不同的轮次也不应直接用来推导切换窗口的因果效应。
- 不与旧版本、旧窗口模式、strict 焦点策略或旧工作负载数据合并，不据此宣称修复带来性能提升。后续应匹配版本、资源、协议、焦点策略与环境再比较。
- 本次桌面实验不覆盖朋友原机或其他硬件。2026-10-05 后续已归档朋友 GTX 1650 原机修复后的九轮结果，并按用户确认列为指定低端性能基准，见 [[Benchmark-GTX1650低端机基线]]；指定中端 Y9000P 的有效基线及 AMD/Intel Windows 真驱动验证仍待补齐。两份日常失焦记录都不宣布 M2 整体验收或后续性能里程碑达标，也不替代手动玩法验收。
