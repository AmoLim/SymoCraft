## M3-T5-CT01 组件类型范围

### 依据与适用范围

[T5 范围](../../../scope/project-scope.md#m3-t5-完成-ecs内存契约与整体验收)要求核对组件增删、所有权、引用失效及失败行为。当前[公开头](../../../../game/modules/ecs/include/symocraft/ecs/registry.h)仍限制 standard-layout 且 trivial 的组件；这里记录未来目标，不把正常 C++ 对象生命周期支持写成现役能力。

沿用现役[module-boundaries](../../specs/module-boundaries/spec.md)与[simulation](../../specs/simulation/spec.md)边界；[T4 设计](../archive/2026-10-19-m3-t4-application-simulation/design.md)及[实体装配选择](../archive/2026-10-19-m3-t4-application-simulation/decisions.md#q01-实体装配入口)仍独立有效。本项不接管 caller 的组件注册责任、不改变物理核心的中立小值输入，也不扩大 T4 的局部修补范围。

### 候选与选择

| 方案 | 类型范围 | 权衡与状态 |
| --- | --- | --- |
| 1 仅支持 POD | 继续限制为简单数值、标志及 ID 等 | 限制清楚，但延续构造/析构能力不足；本次未选 |
| 2 支持受约束的常规 C++ 类型 | 可包含构造函数、容器及资源所有权，须满足下述约束 | 初版已选；摆脱旧字节池限制，同时控制删除与清理的异常复杂度 |
| 3 扩大类型范围并按需采用特殊存储策略 | 评估不可移动、需要稳定地址等不满足初版能力的必要类型 | 仅列后续候选；可能增加存储策略、查询和失败路径的维护成本，未选择具体策略，也不承诺支持任意 C++ 类型 |

上述成本为定性判断，未进行实现或性能测量。

### 初版方案 2 的约束

- 注册类型须满足不抛异常的移动构造、移动赋值和析构要求；不满足时在编译期拒绝。具体容器及其 allocator 组合也逐类型核对，不因属于标准库类型就默认全部可用。
- 构造允许失败，但构造/分配失败后的提交、引用失效及恢复保证另行确定；本项不预先承诺整实体或整次模拟回滚。
- 严格新增操作按显式参数构造组件；获取或新增操作仅适用于可默认构造类型。讨论中的 `Emplace<T>`、`GetOrAdd<T>` 不在此冻结最终命名或签名。
- 初始化遵循类型自身的构造语义，不以整块字节清零替代对象构造，也不承诺所有数值成员自动为零。
- 组件构造、移动和析构不得重入所属 Registry。支持资源所有权不改变既有模块所有者、借用寿命及 SDK 隔离边界，也不要求新增资源型组件。

### 方案 3 的评估触发条件

满足以下任一真实需求时启动评估，不自动采用方案 3：

- 生产消费者确有组件必须不可移动或保持地址稳定，且改用 ID、外置所有者或调整访问方式仍无法合理满足其语义；给出具体类型、消费者、寿命和无法替代的理由。
- 必需组件无法满足初版的不抛移动约束，且调整类型设计或使用方式无法合理解决；给出实际限制及其对装配、删除、清理的影响。

实体数量增加、新增普通组件或 EnTT 提供更多能力，不单独触发选型。不可默认构造也不单独触发，显式参数构造仍属于方案 2 的范围。

### 触发后的选型与采用条件

重新比较以下方向，不把评估触发视为已决定升级：

| 方向 | 必须比较的内容 |
| --- | --- |
| 保持方案 2，调整数据组织 | ID/外置 owner 等方式能否表达真实需求，以及额外查询与寿命管理成本 |
| 仅为必要类型采用特殊存储 | 稳定地址或其他存储策略的适用类型、空洞/间接访问、引用失效和删除规则，避免无差别迁移其他组件 |
| 更广泛地扩大类型支持 | 真实复用需求、类型限制、存储/查询复杂度及消费者迁移成本，不能直接取消全部约束 |

采用前须明确组件的地址与引用稳定性、删除与析构、构造/分配失败及清理边界，并比较代表性场景的内存和遍历成本；不凭类型支持范围宣称性能收益。

既有实体身份和查询安全方向不得被静默削弱；任何必要调整须明确提出。具体策略、目标规格、实施范围及验证方法另行审核并取得授权，不预建特殊池、稳定地址机制或兼容框架。

## M3-T5-TH01 线程使用范围

### 依据与选择

沿用[T5 范围](../../../scope/project-scope.md#m3-t5-完成-ecs内存契约与整体验收)与[T4 设计](../archive/2026-10-19-m3-t4-application-simulation/design.md)的所有权、同步借用、自有结果和部分提交边界。本项规定未来 Registry 的线程使用方向，不表示现有 ECS 已支持线程交接，也不授权修改 T4 调度或接入计算线程。

| 方案 | 使用方式 | 权衡与状态 |
| --- | --- | --- |
| 1 绑定创建线程 | 同一 Registry 仅在创建线程使用 | 线程归属检查直接，但限制整体迁往计算线程；本次未选 |
| 2 外部串行，允许同步交接 | 同一 Registry 的访问由调用方串行协调，可在结束借用并同步后转交另一线程 | 初版已选；允许整体迁往计算线程，不引入同一 Registry 的并行访问契约 |
| 3 受控并行访问 | 在明确读写冲突规则下，对同一 Registry 的独立任务分批并行 | 仅列后续候选；不代表任意入口可并发，也不默认采用全局锁或某个调度库 |

### 初版方案 2 的边界

- 同一 Registry 不承诺并发访问安全，包括并发读取或读写混用；组件指针、引用及查询也属于其访问范围。交接前结束全部查询及组件借用，通过明确同步建立先后关系，交接后原线程不得继续访问。
- 整体迁往一个计算线程不需要方案 3；可由计算线程独占 Registry，呈现侧消费自有显示数据，不持有 ECS 借用。其他 owner 的线程限制仍须分别满足。
- 查询期间的结构修改检查不是锁，也不是通用并发误用检测。初版不预建内部锁、线程池或系统调度器。
- 不因 Registry 实例不同就自动承诺可并行；不同实例的并行使用须在固定 EnTT 版本及实际构建配置下，核对共享类型机制和其他共享状态后另行明确。

### 方案 3 的评估触发条件

代表性生产场景的测量同时表明：模拟线程持续超过已确认预算，主要成本可有效并行，且自有输入快照上的后台计算、所属线程汇总提交等较简单方式仍不足以解决问题，才启动方案 3 的评估。

每村 20–30 个 NPC、迁往单一计算线程、机器具有多核或长期服务化方向，不单独触发升级。触发条件只启动评估，不自动采用方案 3 或授权实施。

### 预期收益、代价与采用条件

预期收益是让同一 Registry 上确实独立的计算利用多个 CPU 核心，缩短模拟推进时间；不是单纯移动线程就增加算力，也不是未经测量的性能保证。

代价包括读写冲突声明和访问约束、任务依赖及同步等待、结构修改的集中协调，以及更复杂的遍历次序、可复现性、异常和部分提交边界；竞态复现、调试与验证成本增加，小负载可能因任务与同步开销反而变慢。上述收益和成本均为定性判断，未实施或实测。

采用前须比较维持方案 2、快照后台任务和受控并行批次，以同条件代表性负载验证实际收益及额外内存/调度成本；明确读写集、借用寿命、结构提交时点、故障处理和次序要求。不得静默改变 T4 的时间预算、部分提交或 CPU/呈现分离契约，也不默认扩大为任意并发读写。具体目标规格、实施范围及验证方法另行审核并取得授权。

## M3-T5-UP01 已有组件的值更新

### 选择、理由与适用范围

2026-10-16 用户确认初版采用方案 1：通过 typed 读取或同步查询回调取得可写组件引用，直接修改已有值；不增加 `Replace/Patch`、自动更新通知或通用脏追踪机制。名称仅用于讨论，不冻结未来接口签名。

| 方案 | 范围与状态 | 权衡 |
| --- | --- | --- |
| 1 直接 typed 值修改 | 初版已选，具体赋值或业务计算由消费者组织 | 贴近现有消费者并控制迁移范围；ECS 不提供任意值修改的自动回滚 |
| 2 额外提供完整值替换 | 仅保留未来候选，尚未采用 | 可集中候选构造与提交契约；增加入口、参数别名、引用失效及失败路径的维护成本 |
| 3 所有修改强制经过受控入口 | 本次未选 | 有利于统一追踪，但须改变已接受的可写引用契约，并迁移全部写入消费者 |

沿用[现役 simulation](../../specs/simulation/spec.md)及[T4 部分推进失败契约](../archive/2026-10-19-m3-t4-application-simulation/specs/simulation/spec.md#requirement-rejection-and-partial-advance-failure)的职责边界；T4 的逐实体候选计算/提交与前序提交保留继续有效。本项不是取消业务层的候选提交，也不把未来 `Replace` 写成当前能力。

### 初版更新与异常边界

- 修改已有组件值不改变实体或组件归属，查询期间允许；不能借值修改绕过结构修改保护或既有类型、借用及所有权约束。
- 字段赋值或用户回调抛异常时，ECS 不回滚此前修改；具体类型和成员自身的异常保证仍有效。查询异常退出恢复对应保护状态，不等于恢复组件值。
- 单纯的值修改异常不自动表示 ECS 存储损坏，不据此自动将 Registry 标为 Failed；已知存储一致性故障仍按其既定契约处理，simulation 是否停止继续遵循 T4，不混同两层状态。
- 需要计算成功后才提交的业务，由消费者明确准备候选并提交；取得可写引用本身不提供事务。新增组件的失败保证不推广为任意字段赋值、整实体或整次模拟的回滚保证。
- 不因底层库具有更新通知就承诺直接引用写入可被自动捕获。

### 方案 2 的评估触发条件

真实生产消费者反复需要完整候选构造成功后才替换旧组件，且分散实现已产生明显重复或错误风险时，启动评估；须给出实际调用位置、所需保证及现有组织方式的不足。

仅因 EnTT 提供 `replace`、实体数量增加或新增组件类型，不触发升级。触发只启动选型，不自动采用或授权实施。

### 评估准则与采用边界

- 比较继续由业务组织候选、提取小型业务 helper 与增加通用 `Replace<T>`，确认是否确有稳定的跨消费者复用需求。
- 明确候选构造或分配失败是否保留旧组件逻辑值，提交能否利用既定不抛移动约束完成；同时规定参数别名、输入移动和外部副作用的保证范围，不能笼统承诺所有构造调用均可回滚。
- 明确实体身份与组件归属是否保持、是否允许查询期间调用、组件引用及内部成员借用的失效条件；不静默用删除再新增实现替换，不削弱现有查询保护。
- 用代表性真实类型核对构造、移动、临时内存和调用开销，以及失败、别名和生命周期契约测试的成本；没有实测时不宣称性能收益。
- 不顺带加入自动通知、通用回滚或整实体事务，也不扩大组件类型支持范围；不得改变 T4 的提交边界。

收益和成本目前均为定性判断。具体接口、目标规格、实施范围及验证方法另行审核并取得授权，不预建未来替换入口或空兼容层。

## M3-T5-DF01 查询后的结构修改

### 选择、理由与适用范围

2026-10-16 用户确认初版采用方案 1：调用方在查询中收集自有数据或非拥有式 EntityId，全部活动查询结束后，通过普通 Registry 接口执行结构修改；初版不内置命令缓冲或自动延迟执行。查询期间禁止结构修改，不因记录处理意图而获得例外。

| 方案 | 范围与状态 | 权衡 |
| --- | --- | --- |
| 1 调用方收集、查询后执行 | 初版已选，业务决定提交时点与失败处理 | 保持执行和错误出口直接，不增加通用命令框架；收集、去重等必要组织由消费者承担 |
| 2 ECS 显式命令缓冲 | 仅保留未来候选，调用方显式提交 | 可复用重复的记录与执行逻辑，但增加参数所有权、次序、身份及失败契约 |
| 3 自动延迟结构修改 | 本次未选 | 接口生效时点随查询上下文变化，错误可能延迟暴露，增加推理与调试成本 |

沿用[T5 范围](../../../scope/project-scope.md#m3-t5-完成-ecs内存契约与整体验收)、[现役模块边界](../../specs/module-boundaries/spec.md)及[T4 部分推进失败契约](../archive/2026-10-19-m3-t4-application-simulation/specs/simulation/spec.md#requirement-rejection-and-partial-advance-failure)。这里记录目标选择，不宣称当前旧 ECS 已具备对应检查，也不改变 T4 的业务提交时点或扩大生产迁移范围。

### 初版执行边界

- 收集项为自有值或非拥有式实体 ID，不保存组件引用、指针或捕获这些借用的延迟闭包；所有嵌套查询退出后才执行结构修改。
- 收集不代表预约成功，执行时仍遵守普通入口的身份、注册、容量及失败检查；不延长 Registry 或实体寿命。
- 多条操作不是事务，前序成功不因后续失败而回滚；重复 ID、执行次序及失效实体的跳过或报错由业务明确组织，ECS 不隐式去重或吞错。
- 查询提前终止或抛异常时，不自动执行已经收集的操作；调用方明确决定丢弃或后续处理，不承诺回滚此前业务值修改。

### 方案 2 的评估触发条件

真实生产消费者反复需要查询内记录、查询后执行，且分散实现已出现明显重复、提交时机不一致或错误处理风险时，启动评估；须给出实际调用位置及现有组织方式的不足。

NPC 数量增加、未来可能并行或底层库具有相关能力，不单独触发升级；触发只启动评估，不自动采用方案 2 或授权实施。

### 评估准则与采用边界

- 比较继续由业务组织、提取业务 helper 与增加通用命令缓冲，确认实际复用收益是否值得额外契约和维护成本。
- 明确命令参数的所有权与寿命，不保存组件借用；评估同一批命令引用尚未创建实体的表示方式、适用范围和失败处理，不预选临时 ID 机制。
- 明确提交时点、执行次序、重复及冲突命令、失效实体的处理，不因记录成功就承诺全部命令可执行。
- 区分记录失败与执行失败，规定前序提交、剩余命令、销毁及重试行为，避免重复执行已成功操作；不默认承诺批次回滚。
- 明确缓冲与所属 Registry、Clear 身份批次及 owner 寿命的关系，不允许旧命令误作用于其他 Registry 或清空后新建的实体。
- 在代表性真实负载上比较分配、暂存内存及执行成本，并覆盖失败、身份和生命周期测试；未实测不宣称性能收益。
- 不顺带引入跨线程提交、自动调度、自动延迟或通用事务，不改变 T4 的提交边界；具体接口、目标规格、实施范围及验证方法须另行审核并取得授权，不预建命令框架。

## M3-T5-TK01 组件类型键碰撞

### 选择、理由与适用范围

2026-10-17 用户确认记录初版方案 1：沿用 EnTT 默认组件类型键，在显式注册时以独立的真实 C++ 类型身份检查碰撞，不同类型占用相同键时具名拒绝后注册者。保持适配较薄，不为理论碰撞预建内部编号分配机制；代价是发生碰撞的两个类型不能同时注册到该 Registry。

| 方案 | 范围与状态 | 权衡 |
| --- | --- | --- |
| 1 默认键加碰撞检查 | 初版已选，注册前检查并拒绝真实类型碰撞 | 复用底层默认访问路径，但存在明确的类型键冲突拒绝边界 |
| 2 项目分配内部存储键 | 仅保留未来候选，按类型分配不同键并适配指定存储访问 | 可避开默认键碰撞，但增加键分配、映射、容量与查询路径的维护成本 |

依据为[T5 范围](../../../scope/project-scope.md#m3-t5-完成-ecs内存契约与整体验收)、[现役模块边界](../../specs/module-boundaries/spec.md)及 EnTT v4.0.0 的[默认和指定存储访问](https://github.com/skypjack/entt/blob/v4.0.0/src/entt/entity/registry.hpp)、[类型信息](https://github.com/skypjack/entt/blob/v4.0.0/src/entt/core/type_info.hpp)。当前[旧公开头](../../../../game/modules/ecs/include/symocraft/ecs/registry.h)仍采用类型 counter；本项是目标选择，不宣称已实现碰撞保护，也不在此冻结第三方版本或启动适配。

### 初版边界

- 同一 C++ 类型重复注册仍幂等；不同真实类型使用相同底层键时，在发布新注册或触碰不匹配组件池前拒绝，已有注册、实体及组件保持不变。
- 检查依据须独立于待检查的类型哈希，不能再以该哈希相等证明类型相同；调试名称不作为类型身份，也不以名称不同自动推定类型不同。
- 不依赖 Release 断言防止错误类型访问；具体类型身份及检测机制纳入适配核对，不在此预选 RTTI 或其他实现。
- 增大哈希位宽不等于证明不会碰撞。该冲突边界不恢复旧的 256 类型限制，也不要求各 Registry 采用相同注册顺序。
- 对外仍为 typed 操作，不暴露内部键或承诺其跨进程、跨构建稳定，不把组件类型键与 EntityId 的容器哈希混为一项契约。

### 方案 2 的评估触发条件

真实必需类型出现默认存储键碰撞，或具体生产消费者证明碰撞即拒绝无法满足需求时，启动评估；给出实际类型、调用方及拒绝对业务的影响。

仅类型数量增加或担心理论碰撞，不单独触发。触发只启动评估，不自动采用自分配键，也不授权实施。

### 评估准则与采用边界

- 比较继续采用碰撞拒绝、使用官方支持的键配置与项目分配内部键，区分降低碰撞概率和处理已发生冲突，不以扩大位宽代替真实类型检查。
- 明确类型身份、键分配、键空间耗尽及映射寿命；保持注册失败不发布半成品、已有注册不变，不恢复跨 Registry 注册顺序耦合。
- 核对注册、typed 增删读取、必需与排除查询及相关内部路径是否仍依赖默认类型哈希；不能只修改注册入口，或把不同类型映射到同一池。
- 比较映射查找、额外内存、查询组织及维护成本；未测量不宣称性能收益。
- 用可控碰撞、跨翻译单元及失败用例验证类型区分和注册原子边界，不以偶然找到自然碰撞作为验证前提。
- 不修改 EnTT 源码，不公开内部编号；具体方案、目标规格、实施范围及验证方法另行审核并取得授权，不预建编号或查询框架。

| 2 显式批量入口 | 仅保留未来候选，一次接受数量或实体 ID 集合 | 可能集中校验、减少重复工作，但增加输入、次序、部分成功及重试契约 |

### 初版边界

- 上层循环逐次遵守普通入口的身份、容量、注册及失败检查；实体创建不代表其业务组件已完整装配。
- 前序成功不因后续创建、装配或销毁失败而自动回滚；上层明确处理已成功、失败及未处理范围，不将多个单次保证组合成整批事务。
- 不因底层已有批量能力或未来居民数量增加，就扩大初版公开面；本项不新增 NPC 装配或游戏规则。

### 方案 2 的评估触发条件

代表性真实负载实测表明单实体循环开销显著影响已确认预算，或多个真实消费者反复需要统一的批次结果与失败报告时，启动评估；给出成本定位、预算依据或实际重复调用位置。

实体数量增加、底层库提供批量入口或对未来性能的推测，不单独触发。触发只启动评估，不自动采用或授权实施。

### 评估准则与采用边界

- 比较继续显式循环、提取业务 helper 与通用批量 API，区分普通调用开销、组件装配及业务计算成本，确认通用接口的真实收益。
- 明确输入数量或 ID 集合的所有权与借用寿命、执行次序、重复 ID、跨 Registry 及失效 ID 的处理，不静默去重、排序或吞错。
- 明确返回实体 ID 及批次结果的所有权、失败位置、前序成功和未处理范围；区分输入预检失败、实际执行失败与结果构建失败，不用模糊成功数量掩盖未知状态。
- 明确剩余操作的处置与重试方式，避免重复执行已成功操作；优先考虑明确的部分成功语义，不默认整批回滚，也不以原始指针或失效借用交接结果。
- 在同条件代表性负载比较执行时间、分配、暂存内存及结果组织成本，覆盖空输入、重复与失效 ID、容量及分配失败、部分成功和重试测试。
- 不顺带引入自动延迟、命令框架、跨线程提交或整批事务，不改变 T4 业务提交与失败边界；具体接口、目标规格、实施范围及验证方法另行审核并取得授权。

- 核对活动查询、借用失效、外部串行及线程交接约束，以及 Clear 前后容量承诺；不得为预分配静默削弱现有身份或查询安全方向。
- 在同条件代表性负载比较增长次数、准备与普通操作耗时、峰值及闲置内存，验证参数边界、失败、已有值和借用契约；不能以过度预留换取表面收益，未测量不宣称性能提升。
- 组件内部字符串、容器及其他资源仍可能独立分配，不承诺通过 ECS 预分配实现全部操作零分配；不顺带引入自定义分配器、收缩接口或固定耗时保证。
- 具体接口、目标规格、实施范围及验证方法须另行审核并取得授权，不预建容量控制框架。

## M3-T5-QO01 有序查询的键比较

### 选择、理由与适用范围

2026-10-17 用户确认初版采用方案 1：显式有序查询使用 `std::less<>` 比较调用方提供的完整值键，不开放自定义比较器参数。多字段顺序可由 `std::tuple` 等值键表达，保持初版接口和验证范围较小；代价是特殊业务顺序须先转换为合适的键。

| 方案 | 范围与状态 | 权衡 |
| --- | --- | --- |
| 1 默认键比较 | 初版已选，调用方提供完整值键，由统一默认规则比较 | 接口简单，组合键可表达常见多字段顺序；特殊规则需要键转换 |
| 2 自定义比较器 | 仅保留未来候选，额外接受调用方比较规则 | 表达更灵活，但增加排序关系、调用状态、异常及验证成本 |

依据为[T5 范围](../../../scope/project-scope.md#m3-t5-完成-ecs内存契约与整体验收)、[现役模块边界](../../specs/module-boundaries/spec.md)及[T4 部分推进失败契约](../archive/2026-10-19-m3-t4-application-simulation/specs/simulation/spec.md#requirement-rejection-and-partial-advance-failure)。当前[旧公开头](../../../../game/modules/ecs/include/symocraft/ecs/registry.h)没有此有序查询入口；本项只记录目标选择，不表示已实现、冻结完整签名或授权适配。

### 初版比较边界

- 默认查询仍不保序；需要顺序时显式使用有序查询，调用方提供自有完整排序键，不以内部分配次序或原生实体编号补齐平局。
- 比较关系须满足严格弱序；双向比较均不成立时视为排序等价，不依赖键的 `operator==`。排序后仍有等价键则具名拒绝，在任何业务遍历回调开始前完成检查。
- 浮点 `NaN` 等破坏排序前提的值不能直接作为有效排序键；调用方须提供满足契约的键，不承诺自动发现任意自定义键比较行为的全部错误。
- 键生成只读，键收集、排序和平局检查期间保持查询保护；键生成或比较抛异常时不开始业务遍历，异常传播并恢复相应查询活动状态，不承诺回滚调用方违反只读约束造成的外部副作用。
- 不改变查询期间禁止结构修改、嵌套查询及业务部分提交的既定方向；本项不新增公共查询对象、内部池重排或跨运行确定性承诺。

### 方案 2 的评估触发条件

真实生产消费者的必要排序规则无法清晰地通过完整值键表达，或者键转换成本经测量影响已确认预算时，启动评估；给出实际消费者、排序规则、当前键表示及其表达或成本问题。

仅为了更灵活、实体数量增加或底层库支持比较器，不单独触发。触发只启动评估，不自动采用或授权实施。

### 评估准则与采用边界

- 比较继续构造完整值键、业务层转换或小型 helper 与开放通用比较器，核对真实复用需求、可读性及维护成本。
- 明确比较器的严格弱序前提、排序等价和平局拒绝规则；同一次调用期间排序关系须稳定，不依赖变化的外部状态，不以附加参数静默恢复内部编号兜底。
- 明确比较器及捕获状态的所有权、同步借用和调用寿命；保持只读及查询保护，不允许通过比较器修改 Registry 结构或相关排序数据，不承诺检测所有隐藏别名和错误比较行为。
- 核对键生成、比较及分配失败的时点、异常传播与保护状态恢复，仍在业务遍历开始前完成排序和平局检查；不扩大为组件值、整实体或 T4 推进事务。
- 用实际排序需求比较键构建、比较调用、分配及暂存内存成本，并核对有效排序关系、等价键拒绝和异常路径的验证成本；未测量不宣称性能收益。
- 具体签名、目标规格、实施范围及验证方法须另行审核并取得授权，不预建自定义比较器框架，不静默削弱已确认的身份、借用和提交边界。

## M3-T5-DBG01 统一 Debug ABI 配置

2026-10-18，批准人：本聊天用户；记录者：Codex（T5 ecs-memory agent）。用户在获知关闭 STL 迭代器检查的代价及统一重建要求后，明确回复“了解，批准该配置，并进行具名记录”。本项登记该次配置选择，不代替完整设计冻结或生产替换入口批准。

- **已选配置：** T5 采用统一 `_ITERATOR_DEBUG_LEVEL=0` 的 Debug 配置方向，保留 `/MDd /Zi /Od /RTC1`。当前已验证环境为 VS2026、工具集 `14.51.36231`、实际编译器 MSVC `19.51.36260.0`、C++20；EnTT 固定候选及 `ENTT_NO_ETO` 不因本选择自动正式冻结。
- **理由与代价：** 消除已复现的 noexcept STL iterator proxy 分配终止路径，而不是在外层捕获该代理异常；接受关闭 checked iterators/iterator debugging 的代价，不因此放宽 A18/A23 或 CT01 的既定要求，也不宣称任意 OOM 均可恢复。
- **一致性要求：** 正式接入时，相关库、公开头消费者及测试必须统一该 ABI 配置并重新构建，不能只给 ECS 或测试单独设置。生产配置传播和组合验证仍属后续实施，不能由隔离实验推定已完成。
- **验证与未选边界：** 配对证据见 [Debug OOM 候选配置](verification.md#2026-10-18-debug-oom-候选配置)。默认 level 2 的历史终止保持失败事实；它仍可作为诊断对照，但不能冒充已选 level 0 的恢复成绩。未选择修改 MSVC STL/EnTT、代理预热或仅靠外层 catch 的修补路线。

本次批准限于 T5 的上述配置方向及已告知的检查损失，不构成 S01.3/S01.4 完成、完整 EnTT/设计冻结、全面生产替换、T5/M3 验收或 Git/sync/archive 授权。当前生产构建尚未因本记录而修改；后续执行继续受唯一 [tasks](tasks.md) 的前置约束。
