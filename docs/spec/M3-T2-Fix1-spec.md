## 问题与基线

预期：已关闭、同卷的临时文件发布成功后，新打开的读者看到完整的新状态；兼容共享读者保有完整旧快照。状态发布失败必须清楚报告，不能因 CSV 或摘要已存在就伪造 `finished`。

当前 [Files::Publish](../../game/modules/foundation/src/files.cpp) 调用 `ReplaceFileW`；返回 `ERROR_FILE_NOT_FOUND` 才尝试一次不覆盖目标的 `MoveFileExW`，其他错误直接抛出。这个分支条件不是独立的“目标已确认缺失”判定，也可能涉及源文件缺失；不得用一次存在性检查代替并发安全。

## 不变契约

- 保持公开 `Files::Publish` 的输入及 `std::system_error` 数值错误传播；Win32 类型和头不泄漏到公共接口，API 与诊断实现保持 foundation 私有，不引入 SDL/图形依赖或扩散到无关 CPU 模块。调用者关闭写流，同卷发布；不增加多写者服务或断电持久性保证。
- 保持兼容 `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE` 读者的旧快照语义；不共享删除读者、被占用源、只读目标、目录目标和缺失源继续明确失败。共享标志的语义见 [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)。
- 不添加发布重试、休眠、吞错、先删目标再移动、忽略 ACL/只读错误或静默换输出位置；首次发布不覆盖竞争者刚创建的目标。新增竞态测试使用受控同步，不靠休眠碰概率。
- `ERROR_FILE_NOT_FOUND` 回退保留原 Replace 错误和最终 Move 结果，成功才返回；不能把缺失源或竞争创建当作成功。
- 失败现场按错误和实际观察记录：1175 保留两文件原路径名；当前无备份的 1176 可使旧目标不存在，1177 可使旧目标改名。不宣称所有错误保留两个路径，也不把路径保留扩大为元数据/流完全不变。依据：[ReplaceFileW 返回值](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)。
- Benchmark 协议/工作负载、有效性判定和 runner 终态要求保持；故障不能被 `summary.yaml` 的正常内容掩盖。图形负载与 Q06/Q07 预算不因文件修复变更。

### F1 诊断要求

API 失败后立即保存 `GetLastError()`；格式化、属性查询和追踪辅助操作在保存之后。测试/采集器不以本地化 `what()` 文本解析数值码，生产异常至少能区分 Replace 与首次 Move，telemetry 保留失败状态阶段。采用最小内部上下文，不为诊断建立新的公共 Win32 类型或修改状态协议 schema。

每个发布事件关联：run ID、UTC 时间、PID/TID、配置、源码/exe SHA、案例/状态阶段、循环下标、API 与 flags、预期成功/预期拒绝、实际数值码和 category、源/目标路径、本测试持有句柄及 share、发布前后存在性/属性及可获得的内容摘要。失败诊断留在包外独立记录；现场查询不可用时写原因，不能将查询错误冒充发布错误。

补齐 closed-target、共享循环、阻塞读者关闭后的恢复、首次发布/回退和各导出状态，不只扩大共享循环的 catch。外层兜底区分发布异常、断言/序列化/写流异常与采集器失败；发布异常缺数值码视为诊断不合格，其他类别不伪造 Win32 码。记录所有实际运行、预期拒绝与意外失败，不因 stderr 为空、格式不匹配或超时丢掉一次运行。

### F2 捕获与对照

1. 在新目录重新构建两配置的真实 `foundation.files`、`performance.export`，先执行无追踪对照，再执行带追踪诊断。每配置、每测试首批最多 20 个独立进程，现场捕获后可结束该批；记录实际次数，不把早停算满额，也不在一次失败内部重试。
2. 使用 [Process Monitor](https://learn.microsoft.com/en-us/sysinternals/downloads/procmon) 或等价文件 I/O 追踪，按测试输出目录过滤，保留所有进程访问，而非只筛测试 PID；关联 Create/Open、Rename/Delete/Disposition、Close 的结果、访问/共享模式及调用栈。抓取覆盖失败前后窗口并保存原生记录与关联摘要，避免只采到失败后的文件状态；句柄快照未命中只表示当时未观测到，不能排除瞬时句柄。
3. 核对真实调用者、测试和 runner 的流/句柄关闭，区分兼容读者、阻塞读者和恢复阶段。查看相关文件/目录属性、ACL、卷/文件系统与重解析情况；只观察，不自动调整权限或驱动。
4. 固定程序、次数与参数，在原 F: 工作区目录和一个全新、普通非同步目录作对照；需要其他磁盘/工作区外写入或系统追踪权限时单独申请。记录安全软件、索引/同步和过滤驱动事实，不能仅因某组件存在就归因。追踪可能改变时序，开启/关闭追踪的结果分别报告。
5. 报告将 API 错误、底层操作状态、责任来源和推断分开。只有时间线与受控对照支持时才下归因结论；若首批不复现或权限不足，保留未定位状态并列下一项有区分力的检查，不继续无界重跑。

不自动关闭 Defender、添加目录排除、卸载过滤驱动、强关其他进程或提升生产程序权限。Process Monitor 的驱动加载/管理员操作及许可确认按执行时权限处理；采集只针对测试目录，避免无关用户数据进入交付报告。

### F3 修复选定规则

能在现有契约内修正句柄寿命、API 使用或调用顺序的，实施对应最小修改并增加回归。若证据表明需要更换发布机制、改变读者行为、引入备份/恢复、多文件协议或环境例外，先提交变更设计，不能用 workaround 隐藏原失败。

涉及用户决策时按 [中央选型规则](project-scope.md#方案决策与选型规则) 提供三至四个真实可行方案，比较契约、失败后状态、兼容性、成本与迁移，并等待确认。当前证据不足，不预先选定另一 Win32 API 或降低发布契约。原因未定位时可先完成 M3-I2，但 M3-I1 与 T2-M08 仍开放。
