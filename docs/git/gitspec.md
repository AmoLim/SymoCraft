- 状态：维护中；各批次范围与交付状态见下文执行记录。
- 建立日期：2026-10-04。
- 适用范围：Symocraft 的提交组织、版本控制配置、验证记录与远端交付。
- 维护责任：Codex 在已授权的工作范围内维护本文和相关 Git 配置；用户决定发布、历史改写及范围变更。

## 目标与授权边界

将积累的工作区改动整理成按依赖排列、意图清晰、可验证和可追溯的提交，而不是按文件夹机械拆分。后续提交继续遵循本规范，但本文件不是无人值守自动提交或定时任务的授权。

当前默认边界：

- 用户已于 2026-10-04 授权在 `feature-refactoring` 分支整理并创建本地提交。
- 本轮明确禁止 push 和 merge branch；不创建 PR、不打标签，不改变远端。
- 用户随后明确本轮“只提交，不编译”：后续不再构建、运行测试、启动游戏或做性能采样，仅做提交内容、路径和 Git 状态检查。该要求优先于下文通用验证流程。
- 不改写已有提交、不强推、不删除用户改动，不借整理历史实施新的功能或 M3 重构。
- 不把历史验收结果当作本次验证，不为重现开发过程刻意提交已知错误版本。
- 本规范不要求新建自动提交脚本、Git hooks 或 GitHub Actions。

## 提交原则

1. 一个 commit 对应一个完整意图。实现、必要构建配置、对应测试和直接相关说明一起提交。
2. 按依赖先后排列，每个代码提交不应依赖后续未提交文件。是否实际构建和运行测试遵循本轮授权；“只提交”任务不自动触发编译或测试，也不将静态检查称为实测通过。
3. 共享文件按改动片段拆分。不能因为文件属于同一目录，就把无关意图绑在一起。
4. 不强求提交数量。如果拆分会产生不可构建或没有独立意义的中间状态，应合并并说明原因。
5. 修复可以随首次引入功能一起提交；只有具备独立意义和可验证边界时才单列修复提交。
6. 每个提交尽量便于审查和定位回归；存在依赖的提交不能保证可任意单独撤销，回退时必须检查后续依赖。
7. 提交前检查实际暂存差异，使用明确的文件或片段清单，不盲目暂存整个工作区。

### 提交信息

沿用现有风格：`type(scope): 中文说明`。

- `feat`：增加能力。
- `fix`：修正已有行为。
- `refactor`：不以改变外部行为为目标的结构调整。
- `build`：构建、依赖和打包配置。
- `test`：独立的测试改进。
- `docs`：规范、设计、说明和历史记录。
- `chore`：版本控制配置等维护工作。

正文说明动机、主要范围、验证结果和已知限制。未运行的验证明确写“未运行”，不能写成通过。scope 优先使用稳定职责名，例如 `world`、`perf`、`benchmark`、`build`、`spec`、`git`。

## Git 配置维护

### `.gitignore`

Codex 负责随项目演进检查和维护忽略规则，优先使用范围明确的路径规则，并留下简短用途注释。

| 内容 | 处理规则 |
| --- | --- |
| 源码、测试、资源、共享 CMake presets、项目文档 | 正常纳入版本控制 |
| `out/`、构建缓存、中间产物、安装目录、测试包 | 忽略，不作为源码提交 |
| 根目录 `.temporary/` | 忽略本地临时回传数据；精选证据仍放在可跟踪的 docs evidence 目录 |
| IDE 个人状态、机器专属 presets | 忽略；不修改共享配置来适配个人机器 |
| `docs/.obsidian/workspace*.json` | 忽略个人窗口、标签页和布局状态 |
| Obsidian 模板、必要共享配置 | 模板纳入；配置逐项审查，不忽略整个 `.obsidian` 目录 |
| `docs/**/evidence` | 保持可见，选择必要日志、小型摘要和少量验收截图 |
| 完整逐帧 CSV、可执行文件、安装包和大型采样输出 | 留在输出目录；不要复制进 docs 后再用忽略规则掩盖 |
| 第三方 `vendor/`、`lib/` 和游戏资源 | 不因扩展名而全局忽略；现有依赖不在本工作中删除 |
| 凭据、令牌、私钥、个人敏感配置 | 不提交；忽略规则不是秘密泄漏防护的替代品 |

新增规则后，用 `git check-ignore -v` 检查预期忽略路径，并确认源码、共享配置和证据仍然可见。不得使用全局 `*.log`、`*.json`、`*.yaml`、`*.png`、`*.lib` 等规则误伤项目输入或验收材料。

`.gitignore` 不会自动停止跟踪已入库文件。需要取消跟踪时，先列出受影响文件、确认用途和授权范围；保留本地文件，不擅自删除或改写历史。对于仍在审查的未跟踪文件，采用明确暂存清单，不强制纳入或隐藏。

### 其他相关配置

- `.gitattributes`：仅在有明确换行、文本或二进制处理需求时新增或调整。不仅为消除提示就引入全仓库换行变更；确有必要的归一化单独提交并检查差异。
- `.git/info/exclude`：仅用于用户明确需要的本机例外，不能替代应共享的 `.gitignore`；修改前确认，不把它当作仓库交付文件。
- Git 用户身份、凭据、全局配置、hooks 和 CI：不擅自更改；需要时单独说明并获取授权。
- Git LFS 或其他新增依赖：先说明收益、兼容性和迁移成本，再决定，不为本次整理默认引入。

## 执行与验证流程

1. 重新检查分支、HEAD、暂存区、已修改及未跟踪文件；识别并保留执行期间用户新增的改动。
2. 建立本次文件与片段清单，以及整理前的内容基线。排除项仍保留在本地，不通过清理工作区来隐藏遗漏。
3. 检查候选材料的体积、个人路径和敏感信息。历史证据保留其原始身份；需要脱敏或排除时明确记录，不能静默改写成新的有效结果。
4. 按当前拆分表准备暂存内容，检查 `git diff --cached` 和空白错误，确认不存在后续阶段的隐含依赖。
5. 在只包含该阶段已提交或候选内容的隔离环境中验证。不能用包含全部未提交成果的工作区构建来证明中间 commit 可构建；不以破坏用户工作区的方式模拟隔离。
6. 当任务包含运行验证时，代码提交执行相应构建和测试，最终验证 Debug/Release，并在原生工具阶段验证仅游戏、仅工具和组合构建边界。“只提交”任务跳过此步，记录未执行，不为完成提交而要求编译。文档与忽略规则提交采用链接、内容和路径规则检查，无需冒充代码测试。
7. GPU 实测、人工玩法、长时间基准和不同机器验收分别记录；未执行的项目列为限制，历史报告不能代替复测。验证失败先处理或说明阻塞，不标记完成。
8. 对比最终内容与整理前基线。除已授权的规范、Git 配置、链接修正及明确记录的必要调整外，原有成果应保持一致。发现需修复功能问题时，不夹带修复，先明确范围。
9. 更新执行记录，交付 commit 列表、各步验证结果、剩余未提交文件与原因。没有另行授权时停在本地，不推送、不打标签、不创建 PR。

## 验收标准

- 所有候选改动均有归属：已提交、待处理或明确排除；不存在无法说明的遗漏。
- 每个提交意图清晰、依赖顺序正确；实际执行和按授权跳过的验证均有真实记录。
- 最终源码和资源没有因整理丢失或被意外修改。
- 忽略规则排除生成与个人状态文件，不隐藏必要项目输入。
- 设计、实现、历史证据和本次实测结果明确区分。
- 远端交付状态真实可查；本地提交不写成已推送 GitHub。
