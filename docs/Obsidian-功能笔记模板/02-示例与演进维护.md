两个 Symocraft 示例是 2026-10-05 从实际笔记和源码抽出的教学快照，未独立运行验收，不替代生产设计或原测试记录。对应的正式笔记整理计划与后续实施记录见 [迁移 Spec](../spec/md-organize/data-system-migration-spec.md)；示例摘录时未执行正式迁移，不把快照状态当成当前实施状态。

**按最容易查阅和维护的形式写：** 并列约定用短表格；明确的调用顺序、分支、循环与提交边界优先用 Mermaid 流程图，文字只补充必要前提、数值、失败后状态与限制。复杂计算可用 C++ 风格伪代码补充，不重复图示流程。验收用“状态｜场景｜预期行为”三列表格，理由和共用约束用短句。

| 区域 | 保留什么 |
| --- | --- |
| 当前设计 | 已落地的成员、不变量、接口及生命周期约定 |
| 本次变更 | 本轮增量、关键伪代码与验收条件 |
| 后续考虑 | 触发条件 → 再考虑的变化 |

两个 D3D12Lab 示例展示功能与类笔记，两个 Symocraft 示例展示数据与系统笔记。数据笔记的当前设计维护语义、表示与存储契约，系统笔记维护读写、处理与顺序契约，三段结构的维护方式相同。模板选择见 [使用说明](00-使用说明.md#数据导向设计怎么选)，新增模板不自动改写现有笔记。

开始时写“本次变更”；实际验收通过后合并到“当前设计”，保留简短理由与证据链接，删除已合并草稿，将变更区恢复为“无”。不变量编号保持稳定，跨笔记引用附所属笔记链接。

- 同一设计主体原地维护，变更区只写增量；按主体选模板，不要求每个模块同时建立功能、类、数据、系统四篇笔记。
- 同一约定只写一处；不把表格内容再用伪代码复述。
- 验收优先维护在关联功能笔记；独立设计没有关联功能或确需独立验证时，在对应设计笔记保留唯一记录。状态初始为 `[ ]`，实际通过后手动改为 `[x]`，失败写 `[ ] 失败`；原因与证据按场景记在表下。同项多个场景全部通过才标记通过；推演不算运行证据。
- 每个函数均有明确审核落点，行为不同的 overload 分开。功能笔记链接设计笔记的权威行为表，不复制完整契约；实现细节留在源码。
