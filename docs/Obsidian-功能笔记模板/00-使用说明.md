# Obsidian 开发笔记模板

从 [D3D12Lab 示例与维护规则](02-示例与演进维护.md) 看功能与类笔记的填法：当前设计 → 本次变更 → 后续考虑。按实际设计主体选择模板，同一主体原地维护，不要求每个模块同时建立功能、类、数据、系统四篇笔记。

## 选择模板

| 模板 | 适用场景 |
| --- | --- |
| [01-轻量功能](templates/01-轻量功能.md) | 日常小功能、明确的逻辑修改 |
| [02-完整功能](templates/02-完整功能.md) | 跨类流程、资源或失败路径较复杂 |
| [03-轻量类设计](templates/03-轻量类设计.md) | 职责明确的小型类 |
| [04-完整类设计](templates/04-完整类设计.md) | 需要明确资源、生命周期及变更增量 |
| [05-技术实验](templates/05-技术实验.md) | 用最小实验确认尚不确定的问题 |
| [06-问题修复](templates/06-问题修复.md) | 复现、定位、修复与回归 |
| [07-数据与存储设计](templates/07-数据与存储设计.md) | 组件、值契约、视图、数据集合的表示、身份、所有权与失效边界 |
| [08-系统与数据流设计](templates/08-系统与数据流设计.md) | 系统函数、数据变换与管线的读写集、处理规则、执行顺序与提交边界 |
| [09-namespace API设计](templates/09-namespace API设计.md) | 函数集合的公开边界、内部 helper、实际 namespace 状态及启动/清理顺序 |
| [10-构建与依赖契约](templates/10-构建与依赖契约.md) | CMake 集成入口、内部检查函数、target 依赖与可见性、配置/构建产物 |

功能、类、数据、系统、namespace API 与构建设计采用三段结构；实验、修复保留各自的专用流程。

一篇笔记选择一个主模板：调用边界用 namespace API，对象用类设计，布局用数据设计，算法与阶段顺序用系统设计，构建关系用构建契约；其余内容通过链接关联。不为 facade、PImpl 或 singleton 再建专用模板，不要求每个模块具备全部类型。

## 数据导向设计怎么选

本项目采用游戏引擎语境的 **Data-Oriented Design（DOD，数据导向设计）**：从实际工作负载、数据访问模式、布局与变换考虑执行代价。用户此前的 DOP 在本项目也指这个语义，后续文档优先写 DOD；不采用以通用不可变数据为核心的另一套 Data-Oriented Programming 方法论。语境参考：[Mike Acton 的游戏开发 DOD 演讲](https://www.youtube.com/watch?v=rX0ItVEVjHc)、[CppCon 官方介绍](https://cppcon.org/third-keynote-2014/)。

- 功能笔记记录行为范围、跨主体流程与验收；类笔记记录真实对象的状态、资源和生命周期。
- 数据笔记回答“数据表示什么、如何存储、谁访问、何时失效”；系统笔记回答“何时读取哪些数据、如何处理、结果何时可见”。不为符合模板建立空类或 System 基类。
- Scene 的顶点格式与 MeshView 适合数据模板；Simulation 的更新流程适合系统模板。Registry 的对象所有权仍可用类模板，存储契约复杂且有独立维护需要时再链接数据笔记。以上是选择建议，不表示已迁移现有文档。
- 两个新模板覆盖引擎 DOD，不等同于 Unity DOTS，也不限定 ECS 或特定存储模型。当前稀疏池、串行执行按现状记录，不默认具有 SoA、archetype、Job System、Burst、SIMD 或延迟命令机制。
- 数据模板先记录工作负载与访问模式，再解释语义、布局、身份、有效期、结构变化与不变量；系统模板记录读写集、实际批处理与数据移动、规则、阶段、提交边界与正确性契约。不适用时注明原因，按需章节可删除，不为填表增加能力。
- DOD 不排斥类、RAII 或组件原地写回，不强制纯函数、全量拷贝或不可变运行状态。只有写了数据契约、用了 POD/ECS 或拆开数据与函数，不能据此认定已经完成 DOD 优化；布局取舍需对应真实访问需求，优化结论需有代表性负载下的测量依据。
- 当前事实、候选方案、未验证假设分开记录；性能结论链接技术实验或 Benchmark 的证据。新模板不替代性能实验模板。

## 使用

1. 将模板放入仓库的 `templates` 文件夹；说明和示例放在外面。
2. 启用 Templates 核心插件，设置模板文件夹为 `templates`。
3. 在设计目录新建并命名笔记，执行 `Templates: Insert template`，填写必要项并删除不适用的按需部分；两个函数行为章节仍保留，不适用时说明原因。

`{{title}}`、`{{date:YYYY-MM-DD}}` 在插入时替换；仅复制文件不会替换。属性保留 `type`、`status`、`project`、`module`、`created`；类笔记另有 `class_name`、`inheritance`。数据和系统模板的 `type` 分别为 `数据设计`、`系统设计`，不设置类名或继承字段。

namespace API 模板使用 `type: namespace API设计` 和 `namespace_name`；构建模板使用 `type: 构建设计`，均不设置 `class_name` 或 `inheritance`。这些属性描述笔记主体，不是图谱板块标签。

首次设计时，“当前设计”写“暂无”，候选设计全部放入“本次变更”。已有笔记只迁移对应章节，不重复插入整篇模板；新模板不会自动更新已有笔记。

## 本项目的板块归属

本项目以 `docs/` 为 vault 根，Templates 的实际配置目录为 `Obsidian-功能笔记模板/templates`，不需要移动模板或修改该设置。

模板源文件不预填板块 tag。模板插入新笔记后，按最终存放目录在 YAML `tags` 列表补齐唯一 `area/*`；已有属性只合并，不覆盖 `type`、`status`、`module` 等值，不重复插入 `tags` 键。正式笔记必须完成归属检查，不能依赖模板自动判断目录。

例如 `project/benchmark/` 下的新笔记使用 `area/benchmark`，`project/architecture/` 下使用 `area/architecture`；`spec/git/` 和 `spec/md-organize/` 下的笔记均使用 `area/spec`。可选 `topic/*` 最多两个，只表示主题，不能替代或增加板块归属。不因采用数据或系统模板新增 DOTS 板块或类型标签。

本目录说明和 `examples/` 中的笔记使用 `area/templates`。复制示例创建项目笔记时，必须移除示例板块并按目的目录重新赋值，不能把示例归属直接带入实现文档。原有 `示例` 标签作为示例笔记的兼容标签保留。

目录与板块对照、图谱查询和新增笔记检查规则见 [文档结构参考](../DOCUMENTATION_MAP.md)；具体验收要求见 [文档与图谱 Spec](../spec/md-organize/mdspec.md)。

## 迭代与验收

写本轮增量 → 实现并实际验证 → 将成立的约定、理由和验收结果合并到当前设计 → 清空本次变更。下一轮复用已有验收，只增加或修改受影响的案例。

验收使用“状态｜场景｜预期行为”三列表格：`[ ]` 未执行，`[x]` 已通过，`[ ] 失败` 未通过。手动改状态；版本、运行入口、失败原因和证据按场景记在表下。同项多个场景全部通过才标记通过，推演不能代替实际运行。

状态手动维护：`草稿` → 按需 `待实验` → `实现中` → `已验证`；暂停或替代时用 `已搁置`、`已废弃`。新迭代可以重新设为草稿，当前设计保留上轮版本与证据。实验被否定也可以是有效结论；证据不足且仍需实验时保留“待实验”。

## 表达与维护

并列约定用表格；有明确调用顺序、分支、循环或提交边界的流程优先用 Mermaid，再用文字补充前提、单位、失败后状态和未验证范围。C++ 风格伪代码只补充图中难以表达的计算，不重复同一流程；理由用短句。模板中的“待填”须替换为实际约定，不为填表或画图增加接口、状态或设计层次。

Mermaid 默认用 `flowchart TD`，节点标明真实 owner/入口，条件边写清判断；系统内部算法与跨阶段调用可拆成不同图，避免把所有细节塞进一张图。图只表示实际顺序，不能把虚线默认为异步任务，或把正常返回画成成功确认；虚线、借用和失败路径的含义用短句解释。函数行为表与不变量仍是详细契约，不被图替代。当前图记录已实现流程，候选流程放本次变更。

功能笔记维护跨主体流程和验收，类笔记维护对象成员与不变量，数据笔记维护表示与存储契约，系统笔记维护处理与顺序契约，namespace API 笔记维护调用边界与状态生命周期，构建笔记维护目标和阶段契约；相同信息只写一处，用链接引用。不变量编号保持稳定，跨笔记引用附所属笔记链接，不能只写可能重名的 D1 / S1。

## 函数行为覆盖

用于 architecture 的八份模板均保留“公开接口预期行为”和“私有函数预期行为”两个独立章节。每个函数都有签名、调用方、正常输出与状态变化、前提、失败反馈及失败后状态、源码与约束落点；行为不同的 overload 分开，不能用“其他辅助函数”代替审核。

类的 public 成员不自动等于模块公开 API；private/protected 标明实际可见性。namespace 没有 C++ public/private，按模块公开头、内部共享头、translation-unit helper 区分；CMake 也没有 private 访问控制，区分项目集成入口与内部检查函数，并注明测试授权。

返回引用、指针、view 或 handle 时注明所有权、有效期与失效条件。区分实现保证、调用者前提、目标行为和已知缺口；当前设计只记录实际实现，未实现目标放本次变更。源码核对不等于运行验证。

没有相应函数时，两表仍保留“不适用：原因”行；纯数据另写聚合构造、复制、移动和字段访问语义，不为填表虚构 getter 或校验器。功能模板两表仅作入口索引，详细契约链接设计笔记；其他设计笔记引用相邻主体时也不复制完整行为表。

先整理的四篇实际架构样板入口见 [示例与维护](02-示例与演进维护.md#函数行为表样板)。用户已授权继续铺开，当前 28/43 篇适用笔记有两类行为表，其余按 spec 队列继续；插入新模板不会自动改写旧笔记。范围、剩余文件与待完成验收见 [Architecture 模板与函数行为覆盖 Spec](../spec/md-organize/architecture-template-coverage-spec.md#2026-10-06-行为表铺开记录)。

验收优先维护在关联功能笔记；没有关联功能或确需独立验证时，在对应设计笔记保留唯一验收记录。数据与系统笔记不复制同一验收结果或性能明细。详细规则见 [类设计说明](01-类设计模板-使用说明.md) 和 [示例维护规则](02-示例与演进维护.md)。

查找待实验事项：`[status:待实验] -path:"templates/"`。历史可交给版本控制，当前笔记删除失效草稿。
